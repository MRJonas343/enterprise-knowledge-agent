# Incident INC-2026-003: Payment Service CPU Saturation

## Summary

On 2026-06-03, payment-service pod CPU saturated at 95% for 22 minutes. The cause was a runaway retry loop against the NorthPay API combined with the same unindexed reporting query seen in INC-2026-002. The permanent fixes were a retry budget, a circuit breaker on the NorthPay client and adding the missing index. It was opened and resolved the same day.

## Root cause

The NorthPay client retried failed calls without an upper bound and without a circuit breaker. When NorthPay became slow, every failed call spawned further retries, so the call rate grew far beyond the inbound authorization rate and CPU saturated.

The saturation was compounded by the same unindexed reporting query introduced in INC-2026-002. The query held database connections and increased the time each in-flight request spent on the CPU, so the retry storm and the query together pushed the pods to 95% CPU rather than stalling at a moderate level.

## Contributing factors

- No retry budget: retries amplified until the service was limited by CPU.
- No circuit breaker on the NorthPay client: the service kept hammering a degraded dependency.
- The unindexed reporting query from INC-2026-002 was still present at the time of this incident.
- Retry behaviour was not covered by a chaos or load test against a degraded NorthPay.

## Resolution

1. Identified the retry storm with the dependency telemetry queries in `runbooks/high-cpu.md`.
2. Lowered the NorthPay retry budget via configuration to stop the amplification.
3. Applied temporary throttling on NorthPay calls to let the vendor recover.
4. Confirmed CPU returned below the 85% threshold and latency returned within SLO.
5. Shipped the permanent fixes: a retry budget, a circuit breaker on the NorthPay client and the missing database index.

The permanent client changes are documented in `architecture/payment-service.md`. The pipeline that must validate such client changes before release is described in `engineering/deployment-guidelines.md`.

## Detection

Detection was automatic. The high-CPU alert (pod CPU above 85% for 10 minutes) paged the payments on-call engineer. The 10 minute window meant the alert fired after the storm had already built, which is a known detection-latency tradeoff addressed in the action items.

## What went well

- The high-CPU alert fired reliably and the runbook diagnosis was accurate.
- Retry idempotency meant no duplicate charges despite the storm.
- The permanent fix addressed both the trigger (retries) and the amplifier (the missing index).

## Lessons learned

- An unbounded retry loop turns a slow dependency into a CPU incident. A retry budget is a safety control, not an optimisation.
- The same unindexed query from INC-2026-002 contributed again, showing that follow-through on action items matters more than the initial fix.
- A 10 minute CPU alert window is too slow for a fast-moving retry storm; a shorter window for payment-service is under evaluation.
- A circuit breaker must exist before a dependency can fail, not after; the NorthPay breaker was built only once the storm had happened.
- Retry amplification is invisible from inbound request metrics alone; the NorthPay call rate must be compared against the inbound authorization rate to see it.
- CPU saturation at 95% leaves no headroom, so latency degrades sharply rather than gracefully once the threshold is crossed.

The client controls and the index are documented in `architecture/payment-service.md`, the triage path in `runbooks/high-cpu.md`, and the release controls that must validate client changes in `engineering/deployment-guidelines.md`.
