## Summary

On 2026-04-12, shortly after a deployment, checkout-api p95 latency rose to 840 ms and the error rate reached 6%. The root cause was exhaustion of the payment-service PostgreSQL connection pool. The exhaustion was triggered by payment-service release v2.31.0, which introduced a long-running reporting query on a non-indexed column. The incident was resolved by rolling payment-service back to v2.30.4. It was opened and resolved the same day.

## Root cause

payment-service v2.31.0 introduced a long-running reporting query that filters the `settlements` table on `settlement_date` and `status`. No index existed on those columns, so PostgreSQL performed a sequential scan over a large table. Each execution held a PgBouncer connection for an unusually long time.

Because each payment-service pod opens a pool of 50 connections, the slow query saturated the pool quickly. checkout-api calls payment-service synchronously with a 2 second timeout and no circuit breaker, so blocked payment requests caused blocked checkout requests. checkout-api p95 latency rose to 840 ms and the error rate reached 6%. The checkout-side behaviour that made the payment degradation user-visible is documented in `architecture/checkout-service.md`.

## Contributing factors

- The reporting query shipped without an index covering its filter columns.
- PgBouncer pool utilisation above 80% for 5 minutes was already an alert, but the query degraded the pool faster than the first alert window.
- checkout-api has no circuit breaker on the synchronous payment-service call, so payment degradation passed straight through to the user.
- The reporting query was not exercised by the pre-deployment load test at production scale.

## Resolution

1. Diagnosed pool exhaustion using `runbooks/database-latency.md`.
2. Confirmed the offending query with `pg_stat_statements` and `pg_stat_user_tables`.
3. Confirmed v2.31.0 was the first release to ship the query.
4. Rolled back payment-service from v2.31.0 to v2.30.4 following `engineering/rollback-procedure.md`.
5. Verified pool utilisation, payment-service latency and checkout-api latency returned within SLO.

The index was added after the incident as a permanent fix, applied concurrently so writes were not blocked.

## Detection

Detection was automatic. The database latency alert (PgBouncer pool utilisation above 80% for 5 minutes) paged the payments on-call engineer three minutes after the deployment completed. The checkout-api latency and error-rate alerts fired shortly afterwards and confirmed the user-visible impact.

## What went well

- The database latency alert fired within three minutes of deployment, before partner reports arrived.
- The rollback decision took under two minutes because the target version was recorded at approval time.
- No payment record was lost or double-charged during the window.

## Lessons learned

- A single unindexed reporting query can take down the checkout path because payment-service pools are per pod and exhaust quickly.
- checkout-api has no circuit breaker, so payment degradation passes straight to customers. This remains the top open improvement.
- A canary that does not exercise the new query at production volume will not catch this class of regression.

The permanent index and the load-test requirement are now enforced by `engineering/deployment-guidelines.md`, and the diagnosis path is captured in `runbooks/database-latency.md`.
