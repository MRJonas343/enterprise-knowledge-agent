# Incident INC-2026-001: Redis Failover Caused Authentication Failures

## Summary

On 2026-02-11, a planned maintenance window on Azure Cache for Redis triggered a primary failover. During the failover, authentication-service could not perform session lookups, so token validation failed and every dependent service returned HTTP 401 responses. The incident lasted 18 minutes and roughly 4% of login attempts failed. It was opened and resolved the same day.

## Root cause

The primary cause was a real dependency failure, not a code defect: authentication-service stores session state exclusively in Azure Cache for Redis, and a primary failover makes those sessions briefly unavailable. During the few minutes of failover the client did not reconnect quickly enough, so session lookups returned errors and callers interpreted them as invalid credentials, producing HTTP 401 responses instead of a retryable error.

## Contributing factors

- The Redis instance is shared between authentication-service sessions and the inventory-service cache, so both workloads were affected simultaneously.
- Session lookups return a generic failure that callers map to 401, which caused a large, visible error burst rather than a small number of slow requests.
- The failover occurred during a planned maintenance window but the reconnect behaviour had never been exercised in production.

## Resolution

1. Confirmed the promoted replica was healthy.
2. Verified authentication-service reconnected to the new primary.
3. Applied temporary login rate limiting to dampen the session rebuild storm.
4. Monitored until Redis CPU and session lookup success returned to baseline.
5. Closed the incident after one hour of stable operation.

The full procedure is documented in `runbooks/redis-failure.md`. The session store design and token TTLs are described in `architecture/authentication-service.md`.

## Detection

Detection was automatic. Azure Monitor detected the Redis failover and paged the identity on-call engineer within two minutes. The authentication-service latency alert for the 250 ms SLO also fired. The fastest human signal was the volume of partner reports about HTTP 401 responses.

## Lessons learned

- A shared Redis instance couples authentication availability to the inventory cache. INC-2026-001 affected both workloads at once.
- Mapping an infrastructure error to HTTP 401 amplified a small failover into a platform-wide error signal.
- Planned maintenance is still an incident risk. A failover drill should be run before any future maintenance window.
- The 18 minute duration was dominated by the session rebuild storm, not the failover itself; failover recovery completed within minutes.
- Roughly 4% of login attempts failed, which is small in absolute terms but highly visible to partners.

The detection and response sequence is now codified in `runbooks/redis-failure.md`, and the session store design is documented in `architecture/authentication-service.md`.
